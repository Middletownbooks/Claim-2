## 2. §6 was right about the screen and wrong about the pipeline

§6's prescription: *"do not wait for a better model to attack a harder object. Use a cheaper one to
look at far more problems, and a better one to attack the one deficit that is stated as an
exponent."* The direction holds and the Hadamard/Sonnet split below follows it exactly.

Its arithmetic does not. §6 said *"a screen that currently produces four candidates per expensive
run could produce four hundred."* **Lesson 24 falsifies that, and it was measured after §6 was
written.** The mapping layer is triage-grade: it identifies which records have a movable number and
states the number too coarsely to gate on. Every candidate leaving it still needs its own promoting
search. So a 400-candidate screen buys 400 gates, and the bottleneck moves rather than closing.

**The screen got cheaper. The gate did not.** That is the correction, and it decides the
architecture.

## 3. Except that the gate is cheaper than it looks, and the project has already proved it

A gate in this project is a bar with a single threshold, a positive control, and a rule that a bar
which cannot be evaluated counts as FAIL. **All of the judgment is spent when the bar is written.
Evaluating it is a well-scoped task** — which is the category the cheap tier is now near-parity on.

This is not a hope. `../playability/GATE_RESULT_SIC.md` is the proof case: it is tiered
`SECONDARY-RELAYED`, *"this session fetched none of it"*, and it was executed by a search
respondent rather than by the instance that designed it. It nonetheless corrected two of that
respondent's own priors — a nine-year-stale hole list, and the numerical/exact conflation at
d=19,603 — **because the prompt was built around those two traps in advance.** A cheap executor
working against a bar designed by an expensive one caught what a reader would have missed.

So the split is not *cheap screening, expensive gating*. It is:

> **Bar design and adjudication are Opus work. Bar execution, breadth, and verification volume are
> Sonnet work. The bar is the interface, and this project spent a month building it.**

## 4. What this means for the live queue

**Opus 5.5 keeps the Hadamard engine, and keeps it at 5.5 rather than moving to Sonnet.** The 8.2
point FrontierCode gap sits precisely on the one task whose value is undiluted, and `PLAN_2092.md`
names an algorithmic deficit as a number — §6's second clause. Do not economise here.

**The four queued promoting searches go to Sonnet 5.5, in parallel, and their bars already exist:**

| search | registered bar |
|---|---|
| U13 D-optimal table | `../fallbacks/prompts/U13_D_OPTIMAL.md` D1 |
| D-optimal transfer audit, item 1 | `../doptimal/PROMPT_U13_TRANSFER.md` §6.1 — one lookup, can end the audit |
| 239 odd perfect number | `../fallbacks/RESULT_MAPPING_B.md` §3, the two risks |
| 345 Erdős–Szekeres | one read of arXiv:2512.24061 |

Four independent single-question tasks with thresholds written before anyone looks. This is the
cheapest the queue has ever been to drain.

**Negative-testing stops being rationed.** Rule 3 of every prompt is *break each verifier
deliberately and confirm it fails*, and this project has shipped two checks that could not fail —
the heredoc-escaped citation regex (D43) and the pair written in one day. Both were mechanical
failures a mechanical pass would have caught. At half price that pass runs on everything rather
than on what someone remembers to check.

**The D-optimal parallel track gets an economic leg it did not have.** `../doptimal/` argues for
parallelism on epistemics: D-optimal has known solutions at trivial cost, which is the graded
control ladder the Hadamard route lacks. Known-answer control instances are the definition of a
well-scoped task. **Before this week the parallel track cost a second Opus. It now costs half of
one**, and the expensive instance stays on the frontier instance where the 8.2 points live.

## 5. Two traps, both specific

**Do not un-chunk the mapping layer because context is cheap.** A, B, C and D were split into
22–31 records each. With 1M context on the cheap tier there is no longer a context reason to split
— and splitting was never the reason. **The chunk boundaries are an experimental design:** they are
why C's falsification of the NONE-rate screen was visible at all, and why D was a held-out slice.
One un-chunked 106-record run would have produced a better-looking number and no test.

**Fan-out makes D45's failure easier to commit, not harder.** D45 records that a replacement metric
got its only out-of-sample test by the accident of processing order, with no bar registered before
the slice was read. With N workers returning N slices, deciding afterwards which one was the test
is trivially easy and invisible. **The fix is free and has to happen before dispatch: name which
worker's output is the held-out slice, in writing, when the work is handed out.**

## 6. The prediction, registered before the fan-out runs

In `../../proof-protocol/ledger.json` as **P-31**, two components, single
thresholds, no middle bands. In short: (a) if any cheap-tier gate execution issues a verdict on a
bar it could not evaluate, the front-loaded-judgment claim in §3 is false and gates go back to
Opus; (b) if the cheap tier ever puts a candidate in the queue without an Opus-designed bar being
written for it first, §6's arithmetic holds after all and §2 above is wrong.
